# PRD-20260603-02 ReAct 模式深化架构与方案设计

## 0. 这份文档在解决什么问题

这份文档不是单独重新发明一套 ReAct。

它要建立在下面这个前提上：

> `PRD-20260603-01 Planner / Executor 深化` 的主要任务已经实现，统一的 `Run / Step(Turn) / ToolObservation / HITL / Workflow State` 基础已经具备。

所以这份文档的重点不是“再做一个和 Plan 平行的新系统”，而是回答下面三个问题：

1. 在统一 Agent Runtime 设计下，ReAct 还差什么。
2. ReAct 应该怎么继续深化，才能和已经落地的 Plan 模式共用同一套底层规则。
3. 对小白来说，ReAct 和 Plan 到底是什么关系，后续应该先补哪里。

一句话概括：

> Plan 更像“先列任务清单，再按顺序做”；ReAct 更像“边看结果边决定下一步”。两者执行风格不同，但底层记录方式、工具边界、状态机和人工介入规则必须统一。

## 1. 先讲结论

### 1.1 PRD-01 完成后，项目现在是什么状态

如果把当前项目理解成一个“会做多步任务的 Agent Runtime”，现在可以这样看：

| 能力 | 当前状态 | 说明 |
| --- | --- | --- |
| Planner / Executor 主干 | 已完成主要实现 | `PlanRun`、`PlanStep`、依赖执行、结果沉淀、blocked、final synthesis 已有真实落地。 |
| ReAct 基础运行时 | 已完成最小可用 + 部分深化 | `ReActRun`、`ReActTurn`、`ToolObservation`、retry、HITL、最终汇总已经具备。 |
| `/chat` 统一聚合 | 已统一到 run 级别 | ReAct 和 Plan 都已经优先从 run-level observations 聚合 documents、citations 和 retrieval trace。 |
| ReAct 高阶自主决策 | 还没有完成 | `/chat` 默认仍偏保守，主要是单工具选择，再进入最终回答。 |

所以更准确的判断不是“ReAct 还没做”，而是：

> ReAct 已经接入统一运行时体系，但还没有深化到“多轮自主决策、多工具策略选择、完整 continuation”的阶段。

### 1.2 本 PRD 的核心目标

本 PRD 的目标不是推翻已有 ReAct，而是把它从“能跑”推进到“更像真正的 ReAct Agent”。

重点补这四件事：

1. 让 ReAct 的“下一步怎么决定”更清楚，而不是只靠当前保守默认 selector。
2. 让 ReAct 的多轮结果沉淀、重试、等待用户、恢复继续，和 Plan 保持完全同一套语义。
3. 让 `/chat` 的 ReAct 真正能逐步走向多工具，而不是永远固定成一轮工具调用。
4. 保证 ReAct 深化不会破坏已经落地的 `platform / application / scenes` 边界。

## 2. 先用小白能懂的话解释 ReAct 和 Plan

### 2.1 Plan 是什么

Plan 可以理解成：

> 先把事情拆成几个步骤，再按依赖顺序去做。

例如：

```text
用户：先查制度，再查库存，最后给建议

Plan:
  step-1 查制度
  step-2 查库存
  step-3 基于前两步给建议
```

Plan 的优点是：

- 结构清楚
- 适合复杂任务
- 容易解释“为什么先做这个、再做那个”
- 容易做依赖控制

### 2.2 ReAct 是什么

ReAct 可以理解成：

> 不先把完整计划一次性写出来，而是每做完一轮，就看结果，再决定下一轮做什么。

例如：

```text
用户：这个商品能不能退？库存够不够？

ReAct:
  turn-1 先查退货规则
  看到规则后，决定 turn-2 去查库存
  看到库存后，决定 turn-3 给最终回答
```

ReAct 的优点是：

- 更灵活
- 适合不确定任务
- 可以根据中间结果临时调整方向

### 2.3 两者关系

它们不是谁替代谁，而是两种任务执行策略：

| 模式 | 更像什么 | 适合什么 |
| --- | --- | --- |
| Plan | 先列清单再做 | 复杂、多步骤、依赖明确的任务 |
| ReAct | 边做边判断 | 目标不完全明确、需要根据中间结果调整的任务 |

但不管是 Plan 还是 ReAct，底层都必须统一：

- 一次完整任务都要有 `Run`
- 每次执行单元都要有 `Step` 或 `Turn`
- 每次工具返回都要有 `ToolObservation`
- 等待用户、失败、重试、取消都要走统一状态机

这就是“统一视角”的核心。

## 3. 与 PRD-01 的统一设计原则

这份文档必须明确引用并继承第一份文档：

- [PRD-20260603-01-Planner-Executor深化架构与方案设计.md](./PRD-20260603-01-Planner-Executor%E6%B7%B1%E5%8C%96%E6%9E%B6%E6%9E%84%E4%B8%8E%E6%96%B9%E6%A1%88%E8%AE%BE%E8%AE%A1.md)
- [PRD-20260603-02-ReAct模式深化架构与方案设计.md](./PRD-20260603-02-ReAct%E6%A8%A1%E5%BC%8F%E6%B7%B1%E5%8C%96%E6%9E%B6%E6%9E%84%E4%B8%8E%E6%96%B9%E6%A1%88%E8%AE%BE%E8%AE%A1.md)

统一原则如下。

### 3.1 原则一：Run 是一次完整任务

无论 ReAct 还是 Plan，`Run` 都表示“一次完整任务”。

所以它们都应该回答同样的问题：

- 用户目标是什么
- 当前任务状态是什么
- 当前执行到哪里
- 发生过哪些工具调用
- 最终答案是什么
- 如果失败，失败在哪

### 3.2 原则二：执行单元只做一件事

ReAct 的 `Turn` 和 Plan 的 `Step` 虽然名字不同，但职责要相似：

| 字段 | ReActTurn | PlanStep |
| --- | --- | --- |
| 目标 | 本轮要做什么 | 这一步要做什么 |
| 工具 | 本轮调用哪个工具 | 这一步调用哪个工具 |
| 输入 | 工具输入 | 工具输入 |
| 状态 | turn status | step status |
| 结果 | observation / summary / error | observation / summary / error |
| 重试 | retry metadata | retry metadata |

简单说：

> Turn 和 Step 都应该是“一个可审计、可恢复、可解释的执行单元”。

### 3.3 原则三：ToolExecutor 是唯一工具入口

不管是 Plan 还是 ReAct，都不能绕过 `ToolExecutor` 直接调工具。

统一链路必须是：

```text
Turn / Step
  -> ToolExecutor.validate_call
  -> ToolExecutor.execute
  -> ToolObservation
  -> 回写到 Turn / Step
  -> 回写到 Run
```

这样做的好处：

- 工具白名单统一
- 工具输入校验统一
- 错误归一化统一
- retry / requires_user 语义统一
- observation 结构统一

### 3.4 原则四：状态机只管理 Run 级状态

统一状态机只回答：

> 这次完整任务现在处于什么状态？

所以：

- `ReActRun.workflow_status` 管整个 ReAct 任务
- `PlanRun.workflow_status` 管整个 Plan 任务
- `ReActTurn.status` 只管这一轮
- `PlanStep.status` 只管这一步

不能出现两套互相打架的状态体系。

### 3.5 原则五：最终回答必须消费 observation

最终回答不是模型“临场发挥”，而是对已经发生过的工具结果做汇总。

不管是 ReAct 还是 Plan，最终回答都应该尽量基于：

- user goal
- 成功执行单元
- successful observations
- citations
- 顺序信息

## 4. ReAct 在 PRD-01 完成后的当前边界

### 4.1 已经有的能力

现在的 ReAct 已经不是空白，已有这些基础：

1. 已有 `ReActRun / ReActTurn / ReActAction / ToolObservation` 合同模型。
2. 已有顶层 `ReActRuntime`，能跑 turn loop。
3. 已支持 `tool_call / ask_user / final_answer / stop`。
4. 已把 observation 同时写入 `turn` 和 `run.observations`。
5. 已支持 retry、waiting_user、final synthesis。
6. 已支持 `/chat`、checkpoint、SSE、HITL 的基础接入。

这说明：

> ReAct 的问题已经不是“有没有”，而是“还不够深”。

### 4.2 还缺的关键能力

当前真正没补好的，主要有下面五项。

#### 缺口一：Action Selector 还不够强

当前默认 selector 仍然偏保守：

```text
第一轮：调一个工具
第二轮：进入 final answer
```

这能保证稳定，但还不是一个真正会“判断下一步”的 ReAct。

#### 缺口二：`/chat` 里的 ReAct 还不是真正多工具

平台层可以支持多轮、多 observation。

但应用层默认路径还没有把这种能力真正释放出来。

也就是说，框架能做到，不代表默认链路已经做到。

#### 缺口三：retry continuation 还需要更清楚

现在已经有 retry 语义，但后续要更明确：

- 是自动重试还是等待外部恢复
- 重试时是否复用原 turn
- 超出预算后如何收敛为最终失败

#### 缺口四：等待用户后的继续执行策略还需要更完整

现在 `waiting_user -> respond / approve / reject` 的基础流程已经有了。

但 ReAct 还需要更明确：

- respond 后是继续当前 run，还是补一个新 turn
- approve 后如何回到正确的下一轮
- reject 后当前 turn 如何在审计上收口

#### 缺口五：默认业务策略还不够“像 ReAct”

ReAct 的价值不只是“能多轮”，而是：

> 能根据问题类型、已拿到的证据、失败情况、风险程度，决定下一轮最合适的动作。

这需要规则策略，后面再逐步给到模型辅助 selector。

## 5. 本次 ReAct 深化的目标

### 5.1 目标

本次 ReAct 深化，建议聚焦下面六个目标。

#### 目标一：把 ReAct 放进统一任务编排模型里

让 ReAct 和 Plan 共享这些共性结构：

- run-level observations
- 统一 workflow state
- 统一 ToolExecutor
- 统一 ToolObservation
- 统一 HITL metadata
- 统一 final synthesis 输入

#### 目标二：让 Action Selector 成为可替换策略位

保留当前默认 selector，但它只能算“默认实现”，不能算“最终设计”。

后续应该让 selector 成为一个可替换策略：

- 默认规则型 selector
- 后续可升级为模型辅助 selector
- 再后续可按 scene policy 自定义

#### 目标三：让 ReAct 多轮执行真正可解释

每一轮都要清楚记录：

- 为什么选这个 action
- 这一轮调了什么工具
- 工具返回了什么
- 本轮结束后为什么继续、等待用户、失败或结束

#### 目标四：让 ReAct 的 retry / waiting_user / resume 更完整

不是只把状态改掉，而是要能回答：

- 现在停在哪一轮
- 为什么停
- 恢复后从哪里继续
- 如果用户拒绝，为什么不能继续

#### 目标五：让 `/chat` 的 ReAct 真正使用完整 run 聚合

最终回答、证据、trace 都要来自完整的 ReActRun，而不是某一条“最新 observation”。

#### 目标六：保留后续模型化升级空间

本次不要求直接上复杂 LLM judge 或复杂 planner。

但要留好接口，后续升级不需要推翻整个结构。

## 6. ReAct 的目标架构

可以把目标架构理解成下面这个流程：

```text
POST /chat
  -> ModeSelector 判断走 ReAct
  -> ToolExecutor 准备当前会话允许调用的工具
  -> ReActRuntime 启动一次 ReActRun
  -> ActionSelector 决定当前 turn 做什么
  -> 如果是 tool_call:
       ToolExecutor 执行工具
       生成 ToolObservation
       写回 turn 和 run
       决定是否继续下一轮
  -> 如果是 ask_user:
       进入 waiting_user
       保存当前恢复点
  -> 如果是 final_answer / stop:
       基于 successful observations 汇总最终回答
  -> 写入 checkpoint / SSE / API response
```

它和 Plan 最大的不同只在一处：

- Plan 的“下一步”由 `depends_on` 决定
- ReAct 的“下一步”由 `ActionSelector` 决定

其他底层规则尽量一致。

## 7. ReActRun 设计

建议把 `ReActRun` 理解成：

> 一次完整 ReAct 任务的总记录。

它至少要回答这些问题：

- 这次任务的目标是什么
- 一共走了几轮
- 每轮做了什么
- 当前停在哪一轮
- 所有工具结果有哪些
- 最终答案是什么
- 如果失败，失败原因是什么

建议统一字段语义：

```python
class ReActRun(AgentRuntimeModel):
    react_run_id: str
    session_id: str
    request_id: str
    mode: Literal["react"] = "react"
    user_goal: str
    workflow_status: WorkflowRunState = "running"
    max_turns: int = 5
    turns: list[ReActTurn] = Field(default_factory=list)
    observations: list[ToolObservation] = Field(default_factory=list)
    current_turn_id: str | None = None
    current_tool_call: ToolExecutionMetadata | None = None
    final_answer: str | None = None
    result_summary: str = ""
    error: str | None = None
    metadata: dict[str, Any] = Field(default_factory=dict)
```

其中最关键的是：

| 字段 | 作用 |
| --- | --- |
| `turns` | 保存每轮执行单元 |
| `observations` | 保存整个 run 的工具结果事实表 |
| `current_turn_id` | 保存当前恢复点 |
| `current_tool_call` | 保存最近一次工具调用元数据 |

## 8. ReActTurn 设计

建议把 `ReActTurn` 理解成：

> ReAct 每一轮“当前决定 + 当前执行结果”的记录。

它至少要记录：

- 这一轮打算做什么
- 用哪个工具
- 工具输入是什么
- 结果是什么
- 有没有失败
- 能不能重试
- 是否需要用户介入

统一语义建议如下：

| 字段 | 含义 |
| --- | --- |
| `action` | 当前轮的动作决定 |
| `input` | 当前轮工具输入 |
| `status` | 当前轮状态 |
| `observation` | 当前轮工具结果 |
| `result_summary` | 当前轮的简短结论 |
| `retry_metadata` | 当前轮重试预算和已用次数 |
| `error` | 当前轮错误 |
| `metadata["hitl"]` | 当前轮等待用户时的恢复信息 |

## 9. Action Selector 深化方案

Action Selector 是 ReAct 的核心。

它负责回答：

> 下一轮该做什么？

### 9.1 当前默认实现保留，但只算“默认档”

当前的 `SingleToolReActActionSelector` 建议继续保留，因为它：

- 简单
- 稳定
- 易于验证

但要明确：

> 它只是默认实现，不代表 ReAct 的最终能力上限。

### 9.2 第一阶段：规则型 selector

建议下一阶段先做规则型 selector，而不是立刻上模型。

规则型 selector 可以根据这些信息判断：

- 用户目标
- 已执行 turns
- 已拿到的 observations
- 当前 allowed tools
- retry metadata
- scene policy

示例规则：

| 条件 | 下一步 |
| --- | --- |
| 没有 previous turns | 调首个推荐工具 |
| 上一轮证据足够 | `final_answer` |
| 上一轮要求补充信息 | `ask_user` |
| 上一轮失败且可重试 | retry 当前工具 |
| 证据不够但还有相关工具 | 调下一个工具 |
| 已到最大轮数 | `final_answer` 或失败收口 |

### 9.3 第二阶段：模型辅助 selector

等规则型跑稳后，再升级为模型辅助 selector。

但模型只能输出结构化动作，不能让它直接跳过平台校验。

例如：

```json
{
  "action_type": "tool_call",
  "tool_name": "inventory_lookup",
  "input": {"query": "sku-1"},
  "rationale_summary": "已经有商品信息，下一步查库存"
}
```

然后仍必须经过：

- allowlist 校验
- input schema 校验
- max turns 校验

### 9.4 第三阶段：scene policy 定制 selector

不同 scene 可以后续定制：

- 首选工具
- 禁止工具
- 高风险工具
- 最大 turn 数
- 是否允许多工具
- 无证据时是 ask_user 还是 stop

这样 ReAct 才能既统一，又支持场景差异。

## 10. ReAct 执行规则

### 10.1 正常成功路径

```text
run_start
  -> turn-1 tool_call
  -> observation success
  -> selector 判断继续
  -> turn-2 final_answer
  -> success
```

### 10.2 多工具路径

```text
turn-1 查制度
  -> 成功
turn-2 查库存
  -> 成功
turn-3 给最终回答
```

### 10.3 ask_user 路径

```text
selector 返回 ask_user
  -> turn.status = waiting_user
  -> run.workflow_status = waiting_user
  -> 保存 current_turn_id
```

### 10.4 tool requires_user 路径

```text
工具返回 observation.requires_user = True
  -> observation 先写入 turn / run
  -> turn.status = waiting_user
  -> run.workflow_status = waiting_user
  -> 写入 HITL metadata
```

### 10.5 retry 路径

```text
工具失败，但 retryable = True
  -> turn.status = retrying
  -> run.workflow_status = retrying
  -> 如果还有预算:
       retrying -> running
       重试当前 turn
  -> 如果预算耗尽:
       failed
```

这里建议短期继续复用当前 turn，而不是新建 retry turn。

原因很简单：

- 更容易追踪
- 更容易序列化
- 更容易做 checkpoint 恢复

## 11. ReAct 结果沉淀规则

统一原则很简单：

> 只要工具返回了结果，不管成功、失败、可重试还是等待用户，都先写 observation。

建议统一写入时机：

```text
turn.observation = observation
turn.observation_summary = observation.result_summary
turn.result_summary = observation.result_summary
turn.error = observation.error
run.observations.append(observation)
run.current_tool_call = observation.execution
```

这样做的好处：

1. 最终汇总有完整事实来源。
2. checkpoint 能解释“到底发生了什么”。
3. HITL 恢复能知道“停在什么地方”。
4. retry / failed 不会丢失错误上下文。

## 12. ReAct 的 HITL 方案

ReAct 的 HITL 主要有两种触发方式。

### 12.1 selector 主动 ask_user

这种情况说明：

> 运行时自己判断，当前信息不够，最好先问用户。

例如：

- 用户问题太模糊
- 缺少关键条件
- 下一步方向依赖用户补充

### 12.2 tool observation 要求用户介入

这种情况说明：

> 工具已经执行到一半，但工具本身判断需要用户确认或补充。

例如：

- 需要审批
- 需要补充参数
- 风险操作前确认

统一 HITL metadata 建议保持：

```json
{
  "mode": "react",
  "react_run_id": "react-xxx",
  "current_turn_id": "turn-2",
  "user_prompt": "需要用户补充的问题",
  "source": "react_action|tool_observation|risk_policy"
}
```

恢复规则：

| 用户动作 | 行为 |
| --- | --- |
| `respond` | 继续当前任务，带着用户补充信息往下走 |
| `approve` | 执行等待审批的工具动作 |
| `reject` | 进入 `cancelled`，不执行副作用 |

## 13. `/chat` 接入深化方案

ReAct 深化不能只在 platform 层停留，最终必须体现到 `/chat`。

### 13.1 当前默认路径

当前 `/chat` 的 ReAct 路径比较保守：

```text
选择 ReAct
  -> 选一个 RAG 工具
  -> 调一次工具
  -> 汇总回答
```

### 13.2 目标路径

目标应该逐步变成：

```text
选择 ReAct
  -> ActionSelector 判断第一轮动作
  -> 执行第一轮
  -> 根据 observation 判断第二轮动作
  -> 继续多轮，直到 final_answer / waiting_user / failed
```

### 13.3 与 Plan 的统一要求

`/chat` 不应该对 ReAct 和 Plan 分别维护两套聚合逻辑。

统一思路应该是：

- 都从 run-level observations 聚合证据
- 都从 run-level state 构造 checkpoint / SSE
- 都通过统一 `ChatAgentRuntimeMixin` 装配工具和上下文

---

## 14. ReAct 的最终汇总方案

最终回答必须来自完整的 ReActRun，而不是只看最后一轮。

建议输入：

```text
user_goal
successful turns
successful observations
citations
turn_order
必要的 trace metadata
```

短期汇总规则可以保持保守：

1. 先汇总每轮成功 observation 的 `result_summary`
2. 合并所有 citations
3. 把所有成功 observation 的 documents 作为回答上下文

这和 PRD-01 的 Plan final synthesis 原则完全一致。

---

## 15. SSE 与 Checkpoint 方案

### 15.1 SSE

建议继续保持现有事件名，不额外引入复杂协议：

```text
start -> history -> tool -> chunk -> done
start -> history -> tool -> waiting_user
resume -> done
error
```

ReAct 的 `tool` payload 应继续包含：

| 字段 | 含义 |
| --- | --- |
| `stage=react_turn` | 当前是 ReAct turn 事件 |
| `react_run_id` | 当前 run |
| `turn_id` | 当前 turn |
| `turn_status` | 当前 turn 状态 |
| `action_type` | 当前动作类型 |
| `workflow_status` | 当前 run 状态 |
| `tool_name` | 当前工具 |
| `turn_count` | 当前已执行轮数 |
| `max_turns` | 最大轮数 |

### 15.2 Checkpoint

checkpoint 必须继续保存：

- `agent_mode`
- `react_run`
- `current_turn_id`
- `current_tool_call`
- `workflow_status`
- `hitl`

这样恢复时才能真正知道：

- 这是不是 ReAct
- 停在哪一轮
- 还在不在等待用户
- 当前 tool call 是什么

## 16. 实施优先级建议

虽然这份文档讲的是 ReAct 深化，但不建议一次性把所有理想能力都上完。

建议分三层推进。

### 第一层：补齐统一语义

优先做：

1. run-level observation 彻底统一
2. ReAct 状态转移尽量统一走状态机
3. `/chat` 聚合彻底依赖完整 run
4. checkpoint / resume 审计完整

这是最值得优先做的，因为它决定了底座是否稳。

### 第二层：补齐规则型 ReAct

再做：

1. 规则型 Action Selector
2. 多工具选择策略
3. 更清楚的 retry continuation
4. 更清楚的 waiting_user continuation

这是把 ReAct 从“最小接入”升级为“可用策略型运行时”。

### 第三层：再考虑模型辅助决策

最后再做：

1. 模型辅助 selector
2. scene policy 定制 selector
3. 更细粒度 SSE
4. 更复杂的 continuation 策略

这样推进更稳，不会一上来就把系统复杂度抬太高。

## 18. 最终验收口径

这份文档的验收口径应该是：

1. 明确承认 `PRD-01` 已经完成主要 Planner / Executor 深化实现。
2. 明确 ReAct 不是重新做一套系统，而是在统一 Agent Runtime 上继续深化。
3. 明确 ReAct 和 Plan 的共性结构：
   - Run
   - 执行单元
   - ToolExecutor
   - ToolObservation
   - Workflow State
   - HITL
   - Final Synthesis
4. 明确 ReAct 接下来的真实重点：
   - Action Selector
   - 多工具策略
   - retry continuation
   - waiting_user continuation
   - `/chat` 完整 run 聚合
5. 明确当前边界：
   - 今天不做 Multi-Agent
   - 不把 Agentic RAG 内部 rounds 变成顶层 ReAct turn
   - 不直接上复杂 LLM judge
   - 不破坏 `platform / application / scenes` 分层

最后可以把这份 PRD 用一句话收住：

> 第一份 PRD 解决的是“任务怎么拆、怎么执行”；第二份 PRD 解决的是“在不确定任务里，下一步怎么判断”。两者不是拆开的两套设计，而是统一 Agent Runtime 的两种执行策略。
