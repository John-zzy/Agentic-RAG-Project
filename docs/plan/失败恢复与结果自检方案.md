# 失败恢复与结果自检方案

## 背景

README P0 中当前优先处理两项：

- 失败恢复：为工具调用、模型调用和长链路任务补齐超时、重试、失败补偿、可恢复执行和幂等控制。
- 结果自检：在多步任务中加入结果校验、失败原因归类和必要时的自我修正。

跨场景业务流转暂缓，后续应和“场景扩展模板”一起处理。当前 scene 扩展能力虽然已经有边界，但模板化不足，不适合在本方案中继续追加跨场景抽象。

## 当前实现概览

当前项目已经具备一些可靠性基础：

- `backend/platform/workflow/state_machine.py` 已定义 `created / planning / running / waiting_user / retrying / succeeded / failed / cancelled` 和合法状态转移。
- `backend/platform/workflow/langgraph/lifecycle.py` 已提供 `mark_retrying()`、`mark_failed()`、`mark_cancelled()` 等 lifecycle 入口。
- `backend/platform/agent_runtime/tool_executor.py` 已统一工具执行结果为 `ToolObservation`，并用 `retryable` 标记可重试错误。
- `backend/platform/agent_runtime/react/tool_turns.py` 已在 ReAct 工具轮次中做局部 retry。
- `backend/platform/agent_runtime/plan/executor.py` 已在 Plan step 中做局部 retry，并支持依赖失败后 blocked。
- `backend/platform/workflow/langgraph/checkpointer.py` 已提供 SQLite checkpoint 和 pending writes 存储。
- `backend/platform/agent_runtime/chat_graph/runtime.py` 已在 HITL 等待点落 checkpoint，并有单进程 resume lock 防重复恢复。

但这些能力仍是局部能力，尚未形成统一的任务可靠性体系。

## 为什么采用 LangChain Guard / LangGraph 优先

本方案应明确优先复用 LangChain / LangGraph 的守护与容错能力，而不是从零重造一套运行时。

LangChain 官方的 guardrails 模式支持在 agent 执行的关键点做校验与拦截，包括 before agent、after agent、model/tool call 周边的 middleware；内置 HITL middleware 也已经覆盖敏感工具调用前的人工审批。LangGraph 官方也提供节点级 `RetryPolicy`、`TimeoutPolicy`、`error_handler`、checkpoint fault tolerance 和 pending writes，可直接承接重试、超时、补偿和失败后恢复。

上一版方案使用 `ReliabilityExecutor / InvocationEnvelope / ResultValidator` 这类项目内名词，是为了表达本项目需要保留的领域状态、审计结构和 API trace；它不应理解为绕开 LangChain Guard。更准确的落地方式是：

- 优先使用 LangGraph 节点级 `retry_policy`、`timeout`、`error_handler` 和 checkpoint。
- 对模型调用优先使用 LangChain middleware，例如 `wrap_model_call` 风格的模型调用守护。
- 对结果自检优先使用 LangChain after-agent guardrail 或本项目 ChatGraph final synthesis 前的等价 guard node。
- 对高风险工具优先对齐 LangChain HITL middleware 的 approve/edit/reject 语义。
- 项目内只补齐 LangChain 不负责的部分：`WorkflowRunState` 映射、`FailureRecord` 分类、幂等存储、副作用补偿协议、现有 `/chat` 响应 trace 和场景策略接入。

因此本方案后续实现应采用“LangChain Guard / LangGraph 原生能力优先，项目平台契约兜底”的组合，而不是纯自研 Guard。

## 目标架构

目标是把“调用可靠性”和“结果可靠性”收敛到 LangChain Guard / LangGraph fault tolerance 体系下，再用项目内契约补齐业务状态、审计和 API trace。

```text
ChatGraph
  -> LangGraph StateGraph node guard
      -> add_node(retry_policy=..., timeout=..., error_handler=...)
      -> SQLite checkpoint / pending writes
      -> node-level failure -> FailureRecord adapter
  -> ReAct / Plan subgraph
      -> model call guard
          -> LangChain middleware / Runnable wrapper
          -> retry / timeout / structured-output validation
      -> tool call guard
          -> LangGraph node retry / timeout
          -> ToolExecutor observation normalization
          -> idempotency / compensation adapter
      -> after-agent result guard
          -> SelfCheckNode / ResultValidationReport
          -> correction route: retry / rewrite / ask_user / revise / fail
  -> FinalSynthesis
```

分层边界：

- `platform.workflow`：继续只负责 `WorkflowRunState`、终态保护、recover/fork 语义，不写模型或工具业务逻辑。
- `platform.agent_runtime`：承载 LangGraph guard 接入、FailureRecord adapter、ResultValidationReport、自检修正路由。
- `platform.models`：在 `ModelClient` 外包一层 LangChain middleware / Runnable guard，不在业务代码里散写模型重试。
- `platform.tools`：声明工具风险、幂等、补偿能力，并把结果统一归一成 `ToolObservation`。
- `application.runtime`：只负责配置装配、API 错误映射、SSE/JSON trace 输出。
- `scenes`：只声明 scene policy，例如是否启用自检、哪些工具高风险、结果校验偏好。

## 失败恢复设计

### 1. LangGraph 节点级 Guard

当前依赖版本为 `langgraph==1.2.0`，`StateGraph.add_node()` 已支持 `retry_policy`、`timeout` 和 `error_handler`。优先在 ChatGraph / ReAct / Plan 的关键节点接入原生能力：

```python
from langgraph.types import RetryPolicy

builder.add_node(
    "execute_step",
    execute_step,
    retry_policy=RetryPolicy(
        initial_interval=0.2,
        backoff_factor=2.0,
        max_interval=2.0,
        max_attempts=3,
        retry_on=is_retryable_node_error,
    ),
    timeout=30.0,
    error_handler=handle_agent_node_error,
)
```

优先接入节点：

- ChatGraph：`react_branch`、`plan_branch`、`final_synthesis`、`persist_turn`。
- ReAct 子图：`select_action`、`execute_tool`、`record_observation`、`synthesize_result`。
- Plan 子图：`create_plan`、`execute_step`、`handle_retry`、`synthesize_plan_result`。
- Agentic RAG 图：`retrieval`、`query_rewrite`、`sufficiency_check`、`final_evidence_synthesis`。

接入原则：

- LangGraph 负责节点级 retry、timeout、error handler 和 checkpoint 恢复。
- 项目内 `FailureRecord` 只作为 `error_handler` 输出的标准化记录。
- 节点 retry 不替代工具幂等；副作用工具必须先有 idempotency key。
- checkpoint 和 pending writes 继续由 `SQLiteLangGraphCheckpointer` 承接，避免已完成节点在恢复时重复执行。

### 2. LangChain 模型调用 Guard

模型调用优先使用 LangChain middleware / Runnable wrapper，而不是在每个调用点手写 try/except。

适配范围：

- `ModelClient.invoke_runnable()`
- `ModelClient.stream_runnable()`
- ReAct `LLMReActActionSelector`
- `GenericAssistantQueryRewriter`
- sufficiency judge 或后续 LLM-as-a-judge
- final answer builder

模型 Guard 职责：

- timeout 与 retry。
- rate limit、连接失败、空输出、结构化解析失败分类。
- 对 selector / query rewrite 的 JSON 输出做 schema guard。
- 将模型调用 trace 写入 `FailureRecord` 或 `model_guard` metadata。

项目内不再单独设计重型 `ModelInvocationEnvelope`；如果需要，最多保留一个 adapter，把 LangChain guard 结果映射为项目 trace。

### 3. 工具调用 Guard

工具调用采用“双层 guard”：

- 外层 LangGraph 节点 guard：对 `execute_tool / execute_step` 做节点级 retry、timeout、error handler。
- 内层 `ToolExecutor` guard：保留 allowlist、schema validation、`ToolObservation` 归一、HITL metadata、幂等和补偿 trace。

`ToolExecutor.execute()` 不再承担完整 retry loop 的唯一职责；ReAct / Plan 当前已有的局部 retry 应逐步收敛为：

- LangGraph 节点 retry 负责 transient exception。
- `ToolObservation.retryable` 负责业务结果层面的可重试判断。
- `RetryMetadata` 只记录事实和预算，不再分散实现 backoff 逻辑。

### 4. FailureRecord

新增稳定失败记录，作为 LangGraph `error_handler`、LangChain model guard、ToolExecutor 的统一输出：

```python
FailureCategory = Literal[
    "tool_timeout",
    "tool_connection_error",
    "tool_validation_error",
    "tool_execution_error",
    "model_timeout",
    "model_rate_limit",
    "model_empty_output",
    "model_schema_error",
    "retrieval_no_evidence",
    "dependency_blocked",
    "policy_blocked",
    "checkpoint_error",
    "cancelled",
    "unknown",
]

class FailureRecord(AgentRuntimeModel):
    category: FailureCategory
    retryable: bool
    message: str
    source: Literal["tool", "model", "runtime", "retrieval", "user"]
    node_name: str | None = None
    tool_name: str | None = None
    step_id: str | None = None
    turn_id: str | None = None
    attempt: int = 0
    max_attempts: int = 0
    metadata: dict[str, Any] = {}
```

落点：

- `backend/platform/agent_runtime/failures.py`
- `ToolObservation.metadata["failure"]`
- `ReActRun.metadata["failures"]`
- `PlanRun.metadata["failures"]`
- Chat response trace 后续暴露摘要。

### 5. 幂等与补偿

幂等和补偿不是 LangChain Guard 自动解决的业务问题，仍需项目内契约。

幂等键：

```text
idempotency_key = hash(session_id, request_id, run_id, node_name, step_id/turn_id, tool_name, normalized_input)
```

建议新增 SQLite 表 `agent_tool_invocations`：

- 唯一键：`idempotency_key`
- 字段：`status / observation_payload / failure_payload / created_at / updated_at`

执行规则：

- 纯读工具可复用已成功结果。
- 副作用工具必须接收或生成稳定幂等键。
- HITL approve 后执行副作用工具前先占位，避免重复 resume 执行。
- 历史记录为 running 且超过 deadline 时，按 recovery policy 标记 unknown 或重试。

补偿协议：

```python
class CompensatableTool(Protocol):
    side_effect: bool

    def compensate(self, *, observation: ToolObservation, reason: str) -> ToolResult:
        ...
```

第一阶段只要求有 trace：`compensation_status=unsupported | skipped | succeeded | failed`。

### 6. Recover API

恢复必须和普通 HITL resume 区分：

- `/chat/resume` 继续只处理 `waiting_user`。
- 新增内部能力 `recover_run()`，后续再决定是否暴露 API。
- `retrying` 可继续当前 run。
- `failed / cancelled / succeeded` 是终态，不能原地变回 running；恢复应 fork 新 run，并记录 `recovered_from_run_id`。
- 恢复起点来自 checkpoint + `FailureRecord` + 幂等调用事实，而不是重新猜测步骤。

## 结果自检设计

### 1. After-Agent Guard 优先

结果自检按 LangChain after-agent guardrail 思路设计：最终输出返回用户前，检查答案质量、证据和多步任务状态。

由于当前项目是自建 ChatGraph/ReAct/Plan 子图，而不是直接使用 `create_agent(..., middleware=[...])`，第一阶段用等价 LangGraph 节点落地：

```text
agent branch result
  -> draft_answer_synthesis
  -> self_check_guard
  -> correction_route
  -> final_synthesis / ask_user / fail_final
```

后续如果将 ReAct/Plan 迁回 LangChain Agent middleware 形态，再把同一 `ResultValidator` 封装成 after-agent middleware。

### 2. ResultValidationReport

```python
class ResultValidationReport(AgentRuntimeModel):
    passed: bool
    failure_reasons: list[str] = []
    categories: list[FailureCategory] = []
    missing_evidence: list[str] = []
    unsupported_claims: list[str] = []
    correction_action: Literal[
        "none",
        "retry_tool",
        "rewrite_query",
        "ask_user",
        "revise_answer",
        "fail_final",
    ] = "none"
    metadata: dict[str, Any] = {}
```

### 3. 校验规则

第一阶段使用规则校验，不依赖 LLM-as-a-judge：

- `answer_mode=evidence_answer` 时必须有 citations。
- `retrieval_trace.final_decision=answer_with_evidence` 但 citations 为空时，必须改为 no_evidence。
- Plan 存在 failed/blocked step 时，不允许最终 run 标记 succeeded。
- 成功 observation 为空时，不允许合成 evidence answer。
- 工具要求用户输入时，必须进入 `waiting_user`，不能继续生成最终答案。
- 副作用工具失败且没有补偿记录时，不能输出“任务已完成”。

第二阶段再加入可选 LLM judge：

- 检查答案是否覆盖用户目标。
- 检查关键结论是否有证据支持。
- 检查多步任务是否有未完成依赖。

### 4. 修正动作

修正必须受 guard 预算约束：

- `max_self_check_rounds=1` 起步。
- `retry_tool` 只允许对 retryable failure，并必须经过幂等检查。
- `rewrite_query` 只允许对 retrieval no evidence 且未 rewrite 过的问题。
- `ask_user` 用于缺参数、范围不清或证据不足。
- `revise_answer` 只允许删除无证据断言，不新增事实。
- `fail_final` 用于不可恢复错误。

### 5. Trace 输出

在 run metadata 中新增：

- `guards.langgraph_retry`
- `guards.model_call`
- `guards.tool_call`
- `guards.self_check`
- `self_check.passed`
- `self_check.failure_reasons`
- `self_check.categories`
- `self_check.correction_action`
- `self_check.rounds`

后续如果前端需要，再映射到 `RetrievalTrace` 或新的 `agent_trace`。

## 实施顺序

### Milestone 1：LangGraph Guard 接入

1. 在 ChatGraph/ReAct/Plan/Agentic RAG 关键节点上配置 `retry_policy`、`timeout`、`error_handler`。
2. 新增 `backend/platform/agent_runtime/failures.py`，让 `error_handler` 输出 `FailureRecord`。
3. 把节点失败写入 `ReActRun.metadata["failures"]` / `PlanRun.metadata["failures"]`。
4. 保留现有局部 retry，但将其标记为兼容路径，后续逐步收敛到节点 guard。

### Milestone 2：LangChain 模型与输出 Guard

1. 为 `ModelClient` 增加 LangChain middleware / Runnable wrapper adapter。
2. 对 selector、query rewrite、final answer builder 增加模型调用 failure 分类。
3. 新增规则型 `ResultValidator` 和 `ResultValidationReport`。
4. 在 ChatGraph final synthesis 前加入 `self_check_guard` 和 correction route。

### Milestone 3：工具幂等与补偿

1. 新增 SQLite `agent_tool_invocations`。
2. 为 `ToolExecutionMetadata` 生成稳定 `idempotency_key`。
3. 副作用工具执行前写入 pending，占位成功后落 observation。
4. 定义 `CompensatableTool` 协议和 compensation trace。

### Milestone 4：恢复执行

1. 定义 `recover_run()` 内部接口。
2. 从 checkpoint + FailureRecord + 幂等调用事实找到最近可恢复 step/turn。
3. `failed` 通过 fork 新 run 恢复，`retrying` 原 run 继续。
4. 增加恢复成功率评测样本。

  - 节点级 retry 后 checkpoint / pending writes 不重复执行已成功节点。
  - failed fork recover。
  - terminal state 不允许原地恢复。
- `backend/tests/test_chat_api.py`
  - API 错误体包含 failure category。
  - self-check 后 follow_up/fallback 行为稳定。

## 非目标

- 不在本阶段处理跨场景 handoff / follow-up。
- 不把 scene 模板抽象塞进本方案；后续应单独设计“场景扩展模板”。
- 不让 failed 终态原地变回 running。
- 不要求第一阶段所有工具都实现补偿；先建立协议和 trace。
- 不强制所有自检依赖 LLM judge，规则校验先落地。

## 验收标准

- 工具、模型、runtime 三类失败都能落到稳定 failure category。
- ChatGraph / ReAct / Plan / Agentic RAG 关键节点优先使用 LangGraph `retry_policy`、`timeout`、`error_handler`。
- 模型调用优先经过 LangChain middleware / Runnable guard，而不是在业务节点里手写重试。
- ReAct 和 Plan 的 guard trace 结构一致。
- 工具 timeout 和模型 timeout 都通过 guard 配置，可测试。
- 副作用工具有幂等键，重复 resume 不会重复执行。
- 多步任务最终回答前必须经过 after-agent/self-check guard。
- 自检失败时可以选择 ask_user、rewrite/retry、修订答案或失败收口。
- `failed / cancelled / succeeded` 终态仍保持不可原地继续执行。

## 实施状态 2026-06-07

本轮 `add-agent-runtime-guard-recovery` 已完成第一阶段在线接入，外部 `/chat`、`/chat/resume` 和 SSE 协议保持兼容，未新增必须同步到 API 文档的响应字段。

已接入的 guard 节点：

- ChatGraph：`react_branch`、`plan_branch`、`self_check_guard`、`final_synthesis`、`persist_turn` 已通过统一 `platform.workflow.langgraph.guards` 注册节点级 `retry_policy`、`timeout` 和 `error_handler`。
- ReAct：`select_action`、`execute_tool`、`record_observation`、`synthesize_result` 已接入同一 guard helper，并把节点失败写入 run metadata。
- Plan：`create_plan`、`execute_step`、`handle_retry`、`synthesize_plan_result` 已接入同一 guard helper，Plan step 的业务状态投影仍由 Plan executor 负责。
- Agentic RAG：`retrieval`、`query_rewrite`、`sufficiency_check`、`final_evidence_synthesis` 已接入同一 guard helper。

已完成的可靠性能力：

- `backend/platform/agent_runtime/idempotency.py` 新增 SQLite 幂等仓储，表名为 `agent_tool_invocations`，用于记录 pending、succeeded、failed 的工具调用事实。
- `ToolExecutionMetadata` 会生成稳定 `idempotency_key`，覆盖 session、request、run、node、turn/step、tool 和 normalized input。
- 副作用工具执行前先写 pending，成功后保存 `ToolObservation`；重复命中同一 key 时复用已完成 observation，不再次执行副作用。
- 已定义 `CompensatableTool` 协议和 compensation trace；未实现补偿的副作用工具记录 `compensation_status=unsupported`。
- HITL approve 后的副作用工具路径已接入幂等保护，重复 resume/retry 不会重复执行同一 approved tool。
- `ChatGraphRuntime.recover_run()` 已作为内部恢复能力落地：`retrying` 原 run 继续，`failed` 默认 fork 新 run 并写入 `recovered_from_run_id`；`failed/cancelled/succeeded` 终态禁止原地恢复为 running。
- 恢复入口会读取 LangGraph checkpoint、pending writes、FailureRecord metadata 和 idempotency facts，作为恢复审计上下文。
- Guarded node failure 在 runtime 内部保留 `FailureRecord`，对 API 边界仍解回业务异常，避免把 LangGraph 内部异常暴露给客户端。

保留的业务语义路径：

- ReAct/Plan 的 `ToolObservation.retryable` 仍表示业务结果层面的重试，不由 LangGraph 节点 retry 替代。
- HITL resume acceptance checkpoint 仍保留，幂等仓储只补强 approve 后副作用工具的重复执行保护。
- Generic query rewrite 的安全 fallback 仍属于 scene 检索策略；schema failure 和模型失败分类由模型 guard 承接。
- 无知识命中的 follow-up/fallback 仍按原 API 行为返回成功响应；self-check 只拦截异常的 requires_user 状态投影。

- 第一阶段只建立补偿协议和 trace，具体业务工具的反向补偿实现后续按工具风险单独补充。
