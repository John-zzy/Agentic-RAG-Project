# PRD-20260606-01 运行时重构缺口修复计划

## 1. 背景

README 里的 P0 项“运行时重构审计”当前还不能勾选完成。项目已经把 `/chat` 主链路接进了顶层 ChatGraph，ReAct 和 Plan 也已经有子图，但还有几类旧胶水代码留在 application 层。

通俗讲：新的图引擎已经装上了，但旁边还有不少旧接线在帮它补事。接下来要做的不是重写整个系统，而是把最容易出问题的接线收回到图节点和 runtime 合同里。

本 PRD 覆盖四个缺口：

- SSE 流式输出过重，前端其实只需要最终回答的打字机效果。
- HITL 人工恢复只在外层 `chat_graph` 成立，ReAct 和 Plan 子图内部还没有真正从等待节点继续跑。
- 结果投影散在 application 层，引用、检索 trace、工具事件、ReAct/Plan 轨迹容易不一致。
- 工具选择策略散在 application 层，默认 RAG 工具、候选工具和工具输入 hint 不够清晰。

## 2. 目标

### 2.1 用户目标

用户在界面上看到的体验应该更简单：

- 正常回答时，只看到答案像打字机一样逐步出现。
- 需要人工补充、批准或拒绝时，界面能收到明确等待事件。
- 工具调用、检索过程、内部 trace 不需要一条条通过 SSE 推给用户。

### 2.2 工程目标

运行时边界应该更清楚：

- ChatGraph / ReAct / Plan 负责流程怎么跑。
- ChatGraphRuntime 负责 checkpoint、resume、lifecycle。
- ChatService 只负责接 API、转响应、兼容前端协议。
- scene 只声明工具和策略，不让 application 层猜工具名。

## 3. 非目标

本次不做这些事：

- 不新增 WebSocket。
- 不重做前端页面。
- 不改变 `/chat`、`/chat/resume` 路由路径。
- 不删除最终响应里的 `citations`、`retrieval_trace`、`react_run`、`plan_run` 等审计字段。
- 不把真实模型内部推理链暴露给用户。所谓“思考部分”只允许是可展示的状态文案或摘要。
- 不一次性重写 Agentic RAG 的底层检索算法。

## 4. 现状与缺口

| 模块 | 当前状态 | 缺口 |
| --- | --- | --- |
| ChatGraph 主链路 | 已经有 `prepare_turn -> select_mode -> route -> react/plan -> final_synthesis -> persist_turn` | 成功、失败、等待、恢复的部分状态仍靠外围补齐 |
| SSE | `chat_stream()` 会手工输出 `start/history/tool/chunk/done` | 前端不需要 tool/history，且这些事件不是 graph 真实流式过程 |
| HITL resume | 外层 `ChatGraphRuntime.resume_hitl()` 能处理等待态 | ReAct/Plan 子图没有从等待节点继续执行，respond 续跑仍在 application 层直接检索和生成答案 |
| 结果投影 | 能返回引用、trace、tool event、agent run | 投影逻辑主要在 `application/runtime/assembly/service_parts/agent_runtime.py` 和 `events.py` |
| 工具策略 | 工具执行走 `ToolExecutor`，scene 能声明候选检索工具 | 默认选哪个 RAG 工具、Plan 用什么工具输入、ReAct hints 仍由 application 层拼装 |

## 5. 需求一：简化 SSE 流式输出

### 5.1 目标行为

`POST /chat` 的 `stream=true` 继续返回 `text/event-stream`，但事件只服务前端展示：

- `start`：本轮开始，返回 `session_id`、`request_id`、`scene`、`agent_mode` 等基础信息。
- `chunk`：答案文字片段，用于打字机效果。
- `thinking`：可选事件，只放可展示状态，例如“正在整理答案”。不放真实推理链。
- `waiting_user`：需要用户补充或审批。
- `done`：本轮完成，返回完整最终结果。
- `error`：本轮失败。

不再要求 SSE 输出：

- `history`
- `tool`
- 每一步 retrieval 过程
- 每一步 ReAct/Plan 内部工具过程

这些调试和审计信息仍保留在最终 `done` payload 或普通 JSON 响应里。

### 5.2 实现建议

- 保留 `ChatStreamEvent` 结构，但收窄业务事件集合。
- `ChatService.chat_stream()` 不再先构造 history/tool 事件。
- 如果模型暂时没有真正 token streaming，就先将最终 `answer` 按短句或固定长度切成多个 `chunk`，先满足前端打字机体验。
- `done.answer` 是最终权威答案，客户端不能只依赖 chunk 拼接结果做持久化。

### 5.3 验收标准

- `stream=true` 正常回答时，事件顺序为 `start -> chunk... -> done`。
- 命中 HITL 时，事件顺序为 `start -> waiting_user`。
- SSE 中不再强制出现 `tool` 和 `history`。
- 普通非流式 JSON 行为不变。

## 6. 需求二：HITL 恢复进入 ReAct / Plan 图节点

### 6.1 问题说明

当前人工等待点能保存到 `chat_graph` checkpoint，但 ReAct 和 Plan 子图内部没有真正“从等待节点恢复”。例如用户 respond 后，application 层会直接构造新的 turn，执行 RAG，再生成答案。这让 ReAct/Plan 的执行轨迹和 checkpoint 审计不够完整。

通俗讲：现在像是总控室知道任务暂停了，但具体车间没有从暂停的工位继续干活，而是外面的人绕了一条临时通道把活做完。

### 6.2 目标行为

ReAct 子图需要支持：

- `ask_user` 后进入 `waiting_user`。
- `respond` 后回到 ReAct 图继续执行，可以再次选择工具或直接回答。
- `approve` 后执行等待中的工具调用，再进入观察记录和后续决策。
- `reject` 后把当前 ReAct run 标记为 `cancelled`。

Plan 子图需要支持：

- 某个 step 进入 `waiting_user`。
- `respond` 后更新当前 step 的输入或上下文，再继续执行该 step。
- `approve` 后执行等待中的 step 工具。
- `reject` 后将当前 step 和 plan run 标记为 `cancelled`。

### 6.3 实现建议

- 在 ReAct 子图增加恢复节点，例如 `resume_waiting_turn`。
- 在 Plan 子图增加恢复节点，例如 `resume_waiting_step`。
- `ChatGraphRuntime.resume_hitl()` 只负责校验等待点、写入 resume payload、重新调用图。
- 删除或降级 application 层直接续跑逻辑，例如 `_handle_clarification_response()` 和 `_continue_react_after_clarification()` 的核心执行职责。
- resume 后的状态变化必须继续走统一 Workflow State Machine，避免终态被再次恢复。

### 6.4 验收标准

- ReAct 等待后，`respond / approve / reject` 都能更新 `react_run`。
- Plan 等待后，`respond / approve / reject` 都能更新 `plan_run` 和对应 step。
- resume 后 checkpoint 中能看到完整 continuation 轨迹。
- reject 必须进入 `cancelled`，不能伪装成 failed 或 succeeded。

## 7. 需求三：结果投影收口

### 7.1 问题说明

现在引用、检索 trace、工具事件、ReAct/Plan 进度很多是在 application 层从各种对象里手工拼出来的。这样短期能跑，但长期会出现字段不一致。

通俗讲：同一份成绩单现在由好几个人手抄，字段越多越容易抄错。

### 7.2 目标行为

platform 层输出统一的运行结果投影，application 层只负责把它转成 API schema。

建议统一结构包含：

- `answer_mode`
- `knowledge_used`
- `citations`
- `retrieval_trace`
- `final_decision`
- `follow_up_question`
- `agent_mode`
- `react_run`
- `plan_run`
- `current_turn_id`
- `current_step_id`
- `current_tool_call`
- `tool_observation`

### 7.3 实现建议

- 新增或强化平台层 `AgentRuntimeProjection` 合同。
- ReAct / Plan 子图结束时都输出同一种投影结构。
- ChatGraph 只负责把该投影写入 `RuntimeGraphState`。
- ChatService 不再理解 ReAct/Plan 内部细节，只做最终 API schema 转换。
- `events.py` 中用于拼 tool progress 的逻辑应逐步下沉或删除；SSE 简化后这部分压力会明显降低。

### 7.4 验收标准

- ReAct 和 Plan 的最终 `citations/retrieval_trace/final_decision/knowledge_used` 字段语义一致。
- 普通 JSON `/chat` 与 SSE `done` 的最终字段一致。
- application 层不再需要从 `react_run.turns` 或 `plan_run.steps` 里猜当前工具事件。

## 8. 需求四：工具选择策略收口

### 8.1 问题说明

当前工具执行边界已经比较清楚，但“选哪个工具、哪些工具优先、Plan 默认用哪个输入”还散在 application 层。尤其是类似“工具名里有 rag/search 就选它”的兜底逻辑，不够稳定。

通俗讲：工具箱已经有了，但每次开工前谁来拿哪把工具，还靠临场猜。

### 8.2 目标行为

工具策略应该由 scene 声明、platform runtime 消费，application 不再猜工具。

建议形成一个 `AgentToolPolicy` 或同等结构，包含：

- `allowed_tools`
- `preferred_tools`
- `default_retrieval_tool`
- `candidate_retrieval_tools`
- `tool_input_defaults`
- `high_risk_tools`

### 8.3 实现建议

- scene 继续负责声明工具、知识源和业务策略。
- runtime 根据 session 的 `mounted_knowledge_sources` 生成本轮工具策略。
- ReAct 和 Plan 图只消费工具策略，不再自己扫描工具名。
- 没有可用检索工具时，返回明确错误，例如 `AGENT_RUNTIME_TOOL_UNAVAILABLE`。
- 保留 `ToolExecutor` 的权限校验和输入校验，不把安全边界挪到 scene。

### 8.4 验收标准

- 不同 mounted knowledge sources 下，allowed tools 正确。
- scene 配置的 preferred tool 优先于默认工具。
- 没有可用检索工具时，不再静默 fallback 到名字猜测。
- ReAct 和 Plan 使用同一套工具策略来源。

## 9. API 与兼容性

### 9.1 保持不变

- `/chat`
- `/chat/resume`
- `/sessions`
- `ChatResponse` 的核心字段
- `ChatResumeResponse` 的核心字段
- session 数据库结构
- LangGraph checkpoint 数据库结构

### 9.2 允许变化

- `stream=true` 的 SSE 事件集合可以从“调试过程型”收窄为“展示结果型”。
- `done` 事件仍携带完整结果。
- tool/history 等调试信息不再作为 SSE 独立事件输出。

### 9.3 前端影响

前端需要按新事件语义消费：

- 收到 `chunk` 就追加到答案区域。
- 收到 `waiting_user` 就展示人工输入或审批控件。
- 收到 `done` 就用完整 payload 覆盖最终答案和引用。
- 不再依赖 `tool` 事件刷新工具调用过程。

## 10. 开发顺序

### 阶段一：SSE 简化

- 收窄 SSE 事件集合。
- 移除 `chat_stream()` 中的 history/tool 必选输出。
- 保持 `done` 返回完整结果。
- 补充 SSE 回归测试。

### 阶段二：HITL resume 图内化

- ReAct 增加等待恢复节点。
- Plan 增加等待恢复节点。
- `ChatGraphRuntime.resume_hitl()` 改为恢复图执行，而不是调用 application 续跑 handler。
- 补充 ReAct/Plan 的 respond/approve/reject 测试。

### 阶段三：结果投影收口

- 定义统一运行结果投影合同。
- ReAct / Plan 子图统一输出投影。
- ChatGraph 写入统一 state。
- application 层只做 API schema 转换。

### 阶段四：工具策略收口

- 定义本轮 `AgentToolPolicy`。
- scene 声明工具策略，runtime 解析。
- ReAct / Plan 统一消费策略。
- 删除工具名猜测兜底。

## 11. 测试计划

### 11.1 SSE 测试

- `stream=true` 成功路径只需要 `start -> chunk... -> done`。
- HITL 路径为 `start -> waiting_user`。
- 无命中 fallback 也走 SSE，并输出 fallback chunk。
- `done.answer` 与普通 JSON 的 `answer` 一致。

### 11.2 HITL 测试

- ReAct `respond` 后能继续工具调用并成功回答。
- ReAct `approve` 后能执行等待工具。
- ReAct `reject` 后进入 `cancelled`。
- Plan `respond` 后能继续当前 step。
- Plan `approve` 后能执行等待 step 工具。
- Plan `reject` 后 step 和 plan run 都进入 `cancelled`。
- 终态后再次 resume 返回明确错误。

### 11.3 投影测试

- ReAct 和 Plan 的 `retrieval_trace` 字段 shape 一致。
- `citations` 不会从失败或中间候选证据误采纳。
- `knowledge_used=false` 时 citations 为空。
- SSE `done` 与非流式 JSON 返回一致。

### 11.4 工具策略测试

- `mounted_knowledge_sources=["documents"]` 只暴露文档相关检索工具。
- `mounted_knowledge_sources=["documents", "ecommerce"]` 暴露电商扩展工具。
- preferred tool 生效。
- 无检索工具时报 `AGENT_RUNTIME_TOOL_UNAVAILABLE`。

## 12. 验收清单

- [ ] SSE 只承担打字机输出和等待/完成/错误通知。
- [ ] ReAct HITL resume 在 ReAct 图节点中继续执行。
- [ ] Plan HITL resume 在 Plan 图节点中继续执行。
- [ ] reject/cancel 状态统一进入 `cancelled`。
- [ ] 结果投影在 platform 层有统一合同。
- [ ] ChatService 不再手工理解 ReAct/Plan 内部执行轨迹。
- [ ] 工具选择策略不再依赖工具名猜测。
- [ ] `/chat` 和 `/chat/resume` 对外主接口保持兼容。
- [ ] 相关测试全部通过。

## 13. 风险与处理

### 13.1 resume 改造风险

HITL resume 牵涉 checkpoint、状态机、工具副作用和会话持久化，风险最高。

处理方式：

- 先补测试，再改实现。
- approve 执行工具前必须先消费等待点，避免重复执行副作用。
- terminal state 必须禁止二次 resume。

### 13.2 SSE 兼容风险

如果前端当前依赖 `tool/history` 事件，事件收窄会影响展示。

处理方式：

- 最终 `done` 保留完整 trace 和工具轨迹。
- 前端调试面板如需要过程数据，可以从 `done` 或会话详情读取。

### 13.3 投影迁移风险

结果投影迁移容易造成字段短期重复。

处理方式：

- 先新增统一投影，再逐步替换旧 application 投影。
- 保持 API response shape 不变。

## 14. 通俗总结

这次修复可以理解成四句话：

- 前端只要看答案像打字一样出来，不需要看每个工具怎么跑。
- 人工恢复要回到 ReAct/Plan 原来的流程里继续跑，不能在外面绕路跑。
- 最终结果只能由一个地方统一整理，不能多处手抄。
- 工具该怎么选要有明确规则，不能靠名字猜。

完成后，README 里的“运行时重构审计”才更接近可以勾选完成。
